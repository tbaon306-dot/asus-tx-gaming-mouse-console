# 逆向与实测记录

写下来是为了省掉下一个人重复踩坑。所有结论都附测量方式，能复现。

---

## 1. SDK 与消息泵不共存

**现象**：程序启动后静默消失，退出码 `-1073740791`（`0xC0000409`，`STATUS_STACK_BUFFER_OVERRUN` / fail-fast）。没有异常、没有堆栈、没有 Windows 错误框，进程直接没了。

**定位过程**：最初以为是"启动竞态"，试过下面这些，全部无效：

| 尝试 | 结果 |
|---|---|
| 把 stdout 重定向到 NUL（怀疑 SDK 往 stdout 写导致） | 仍然崩 |
| 控制台版 vs 窗口版 | 控制台版也崩（5/8） |
| 先预热一个子进程，再调主进程 | 无效 |
| 服务已就绪 vs 冷启动 | 无效 |
| 杀掉宿主的竞态 | A/B 两组同样崩 |

**真正的变量是消息泵。** 五种形态各跑 8 次：

| 形态 | 崩溃次数 |
|---|---|
| 主进程，无消息泵 | **0 / 8** |
| 后台线程，无消息泵 | **0 / 8** |
| 后台线程 + 一个隐藏 Form（有消息泵） | 4 / 8 |
| 后台线程 + 隐藏 Form，随后主进程再调 | 2 / 8 |
| 主进程 + 正常消息泵 | 1 / 8（另有多例表现为卡死） |

再加一组**同时刻交替对照**：同一秒钟里，控制台程序 6/6 成功，GUI 程序 3/6 崩溃。同样的 DLL、同样的报文、同样的设备——唯一差别是有没有消息循环。

**结论**：SDK 内部大概装了某种钩子/窗口子类化，与调用线程的消息泵冲突。无解，只能隔离。

**解法**：界面进程绝不 `LoadLibrary`。所有调用转给 `--host` 子进程（无窗口、无消息泵），走 stdin/stdout，一行一个请求：

```
→  C <base64(XML)>        调用 ExecuteFunction
→  E                      枚举
→  Q                      退出
←  R <ret> <base64|->     结果
```

子进程崩溃就重启并重试一次，另有 25 s 看门狗。冷启动崩溃率从约 30% 降到 **0/10**。

顺带一个发现：**任何形式的 stdout 重定向都不要碰**。早期为了"屏蔽 SDK 输出"做过 `stdout → NUL`，反而更容易触发崩溃，后来删掉了。

## 2. 轮询率是假的

设备上报 `polling_rate` 可写，写 1000 Hz 也返回 `1`，界面看起来"成功"了。实际不是。

**测量方法**：Raw Input（`WM_INPUT` + `RIDEV_INPUTSINK`），按 `RAWINPUTHEADER.hDevice` 归属到具体设备，只统计 `HID#VID_0B05&PID_1A8D&MI_01` 这个鼠标集合。

**结果**：7.000 秒内 656 个报文，间隔中位数 **8.00 ms**，直方图集中在 7–9 ms → **约 125 Hz**。

**排除测量误差**：用 `SendInput` 以 1000 Hz 注入 3000 次移动，`WM_INPUT` 捕获率 100%——测量链路本身没有丢帧，125 Hz 是设备真实输出。

**其他路径也试过**：

- `IOCTL_HID_GET_POLL_FREQUENCY_MSEC`：用户态不可用，功能号 `0x100`–`0x112` 全部返回 `err=1`。
- 直接打开鼠标集合 `MI_01`：非提权打不开，`err=5`（拒绝访问）。
- 设备能力描述 `caps.json` 里确实写着支持 125/250/500/1000，默认第 3 档——但那只是"声明支持"。
- **奥创中心自己也改不动**，同样的 125 Hz。

**结论**：这是 P310 在 2.4G 下的固件行为，软件层无解。本项目因而在 UI 上如实显示，不假装生效。

## 3. 板载保存必须让开奥创

`profile_function=3`（保存到板载）在奥创运行时返回 `1`，但断电后什么也没变——**"指令被接受"和"写进了闪存"是两件事**。

`asus_framework.exe` 会持有设备通道；它一退出，保存才真正落盘。

麻烦在于它由 `ArmouryCrateService`（**SYSTEM**）拉起，普通用户杀不掉：

- 非提权的 `Stop-Process` 对 SYSTEM 实例**静默失败**——不报错，PID 也不变，看起来像"杀了但没死"。
- `Stop-Service ArmouryCrateService` 报"无法打开计算机上的服务"。

正确顺序（`tools/stop-ac.ps1`，需管理员）：

1. `Stop-Service ArmouryCrateService`、`Stop-Service ArmouryCrateControlInterface`
2. 再逐个 `Kill` `asus_framework` 及其兄弟进程（`ArmouryHtmlDebugServer`、`ArmourySocketServer`、`ArmourySwAgent` 等）
3. 等 1 秒复查，确认没有残留

两个服务的启动类型都是「自动」，**重启后会自己回来**，届时需要重新执行。

验证：在完全零奥创的状态下（进程列表为空、两个服务 Stopped），读设备、写性能、写按键、保存板载、切换配置档全部 `ret=1`，且 GUI 正常——项目目标达成。

## 4. 无线鼠标休眠时读数是垃圾

空闲几分钟后，鼠标进入省电休眠。此时 SDK 不报错，而是返回一堆看起来"正常"的假数据：

```
固件 = 0          当前档 = 1         DPI = 100（最小值）      写入 → ret=0
```

这不是设备坏了，动一下鼠标就恢复（固件回到 `1.00.06`）。

程序侧的判断依据：`version` 字段为 `"0"` 或空、或 `currentdpi` 解析失败，即可判定休眠。UI 会提示"动一下鼠标再点重新读取"，并把读数显示为 `—（休眠）`。**不要**直接把这些值写回去，会把配置写坏。

## 5. 按键读回来不是真相

`data_number 1` 返回 27 个固定槽位，顺序是设备内部顺序（1=左键、2=右键、3=中键、4=滚轮上、5=滚轮下、6=DPI1、7=DPI2、8=Ctrl+V、9=Ctrl+C…），**和写入时 `source_key` 的顺序不一致**。

更关键的是，这份数据来自**主机侧缓存**，刚写进去的映射不会立刻反映出来。

**处理方式**：本项目把按键状态存进自己的文件（`%LOCALAPPDATA%\ASUSMouseConsole\state\native-buttons-profileN.txt`），首次运行从旧版网页留下的快照导入，之后以自己为准。

## 6. `data_number 0` 里没有型号名

只有 `version` / `rf_version` / `profile` / `profile_number` / `currentdpi` / `currentdpichannel` / `usb_version` / `type` / `stick_mode` / `booster_version`。

设备型号是拿 PID 硬映射的（`6797` → `ASUS TX GAMING MOUSE (P310)`）。

## 7. 第四档是幽灵

`profile_number` 报 3，但把 `profile_index` 设成 4 仍能读到数据（`1600/100/?/?`，`polling=125`）——是未初始化的内存，不是真实配置档。UI 只按 `profile_number` 渲染可用的档位。

## 还没验证的

诚实记录一下没做完的：

1. **板载持久性没做断电验证**。零奥创下保存返回 `1`，但没有关掉鼠标电源再开机对比过。需要一次物理断电才能闭环。
2. **改键后的实际按键效果没按过**。写入返回 `1`，但"按下侧键真的变成了 Ctrl+C"这一步没有人实际按过——写入成功不等于行为改变。
